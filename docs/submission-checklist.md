1. **Prepare the listed project fields.** The public guide lists the fields below but does not identify each field's requiredness or give text-length caps. Follow the live form's markers and validation. The writing lengths here are drafting targets, not NASA limits. [Project Submission Guide](https://www.spaceappschallenge.org/resources/project-submission-guide/)

| Field | What to prepare for this game |
|---|---|
| Project Name | A consistent working title, such as One Last Signal. |
| High-Level Project Summary | Approximately 100–150 words: who plays, the mission-design problem, the complete playable loop and demonstrated benefit. Revise to match what actually ships. |
| Link to Project Demo | A public short video or slide deck showing the actual game and a real engineering consequence. |
| Link to Final Project | Prefer the playable game URL. Link the public HackathonNASA repository and instructions nearby. A repository is an accepted final-project location, but immediate play is this plan's recommendation. |
| Detailed Project Description | Approximately 500–800 words covering objectives, building/operations/replay, coupled constraints, actual NASA use, architecture, testing and honest limitations. |
| Use of Super Intelligence (SI) | Approximately 100–200 words accurately listing actual tools/models and contributions: research/planning, coding, debugging, tests or assets. Separate development assistance from runtime functionality. |
| NASA Data | Exact source URLs and what each actually controls or contributes. Separate real constants/imagery from synthetic gameplay values. |
| Space Agency Partner Data and Other References | Actual partner resources, libraries, code, assets, game inspirations and licenses. State no partner data used if true; still credit other material used. |

2. **Make the demonstration compliant.** Use a video of at most **30 seconds**, or at most **seven slides including title/introduction**. An over-limit demo is ineligible for Global Judging. A 29-second cut leaves a small margin. Keep a longer walkthrough supplementary. Use English for the project page and linked materials; other-language video speech requires English subtitles. [Judging & Awards Guide](https://www.spaceappschallenge.org/resources/judging-awards-guide/)

For the proposed video, show the mission in seconds 0–4, configuration in 4–10, a real constraint in 10–16, actual redesign/results in 16–23, and play link/provenance in 23–29. Keep figures readable. Use captured results from the exact submitted build; do not animate invented science gains. The written entry should explain the details that cannot fit in the clip.

3. **Check the event and scientific evidence.** Local teams may have 1–6 people; Universal requires 2–6 for Global Judging. Members must be registered, accepted at the same event and listed before closing. One developer is not necessarily a one-person team. At least one NASA resource is necessary for Global Awards; partner data is optional. The five criteria—Impact, Creativity, Validity, Relevance and Presentation—each receive 1–5 scores, without published percentage weights. [Current judging guide](https://www.spaceappschallenge.org/resources/judging-awards-guide/), [Participant FAQs](https://www.spaceappschallenge.org/resources/participant-faqs/)

4. **Keep originality and assistance truthful.** The user confirms that the game ideas are their own. Record that concept origin and disclose this session's AI-assisted research/technical planning plus any actual later coding, debugging or asset work. The submission guide permits SI assistance while saying it should not originate the solution idea. Generated images/video need visible SI watermarking; generated code/audio/data need descriptive-text and metadata acknowledgement. SI-generated material must not use or modify NASA branding. [Submission Guide](https://www.spaceappschallenge.org/resources/project-submission-guide/)

Use an explicit project license and retain third-party source/license records. The event terms require freely available or OSI-open-source original solution content and state an Apache 2.0 default if a license is not selected. This is the event's rule, not a general GitHub licensing assumption. Exclude recognizable names, voices or likenesses of under-18s from submission material; obtain the necessary rights/consent for featured adults. Game-only footage avoids exposing student playtest identities. [Event Terms & Conditions](https://www.spaceappschallenge.org/legal/)

5. **Build this supporting packet in the repository.** These are proposed project files, not separate mandatory uploads:

```text
README.md                         Play link, controls, build/run instructions
LICENSE                           Deliberately selected project license
docs/submission.md                Final field-by-field copy
docs/sources.md                    Source → actual use, credits and licenses
docs/simulation-assumptions.md     Fidelity, fictional specs and synthetic data
docs/ai-use.md                     Accurate contribution record
docs/demo-script.md                Required short-demo cut
docs/implemented-features.md       Shipped capabilities versus roadmap
```

Record the exact commit/build, two reproducible design configurations and the actual resulting metrics. Keep a local production build and backup recording. Put the source manifest in the game as well as the repository so judges can inspect it without reading code.

If editing before closing, resubmit and check again. [Submission Guide](https://www.spaceappschallenge.org/resources/project-submission-guide/)
